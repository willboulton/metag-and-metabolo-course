# TODO — Bioschemas markup improvements

The [Bioschemas TrainingMaterial](https://bioschemas.org/profiles/TrainingMaterial/1.0-RELEASE)
markup currently passes all **Minimum** requirements on every page (validated across the
built site — see the validation run in the project history). The items below are all
**Recommended** (or nice-to-have) enrichments — nothing here is a failure, and the site is
valid to publish without them. They raise the "marginality" coverage and make the metadata
more machine-actionable for training-material aggregators such as
[TeSS](https://tess.elixir-europe.org/).

Files involved:
- `_data/bioschemas.yml` — course-level record (emitted on the landing page).
- `_includes/bioschemas.html` — Liquid that emits the course-level record and per-page records.
- `modules/*/_posts/*.md` — per-page front matter (`description`, `keywords`, `teaches`, …).

---

## 1. Use `DefinedTerm` with ontology IDs for `keywords` and `about`

**Why.** The profile prefers controlled-vocabulary terms over free text. Aggregators can then
match content by ontology ID rather than string. [EDAM](https://edamontology.org/) is the
standard ontology for life-science topics; the Bioschemas examples use it.

**What.** Replace (or supplement) the plain-text `about` entries in `_data/bioschemas.yml` with
`DefinedTerm` objects. Keep a few plain-text `keywords` too — mixing text and DefinedTerm is
allowed.

**Candidate EDAM topics** (verify each at <https://edamontology.org/> before committing —
IDs/labels must match exactly):

| Concept | EDAM topic (verify) |
|---|---|
| Metagenomics | `topic_3174` |
| Metabolomics | `topic_3172` |
| Microbial ecology | `topic_3697` |
| Metabolomics / mass spectrometry | `topic_3172`, `topic_3520` |
| Statistics and probability | `topic_2269` |

**Example** (shape to add under `about:` in `_data/bioschemas.yml`):

```yaml
about:
  - "@type": "DefinedTerm"
    "@id": "http://edamontology.org/topic_3174"
    inDefinedTermSet: "http://edamontology.org"
    termCode: "topic_3174"
    name: "Metagenomics"
    url: "https://edamontology.org/topic_3174"
  - "@type": "DefinedTerm"
    "@id": "http://edamontology.org/topic_3172"
    inDefinedTermSet: "http://edamontology.org"
    termCode: "topic_3172"
    name: "Metabolomics"
```

`jsonify` renders this as-is, so no change to `_includes/bioschemas.html` is needed for the
course-level record. For **per-page** `keywords`/`about` as DefinedTerm, the include currently
passes front matter straight through `jsonify`, so a post can already set structured objects in
its front matter — confirm the rendered JSON on one page before rolling out to all.

**Acceptance.** Landing-page `about` entries are `DefinedTerm` objects with resolvable
`@id`/`url`; validator still reports 0 errors.

## 2. Add `timeRequired` (course and pages)

**Why.** Recommended property; lets learners and catalogues see expected effort.

**What.**
- Course level (`_data/bioschemas.yml`): add an ISO-8601 duration for the whole course, e.g.
  `timeRequired: "P4D"` (4 days) or an hours estimate like `"PT20H"`.
- Per page: add `timeRequired` to post front matter where known (e.g. `timeRequired: "PT2H"`),
  and extend `_includes/bioschemas.html` to emit it:

```liquid
{% if page.timeRequired %}"timeRequired": {{ page.timeRequired | jsonify }},{% endif %}
```

Place the line alongside the other optional per-page fields (before `isPartOf`).

**Note.** The GIBA-course day mapping is already in the content (e.g. "day 3 workshop",
"day 4"), so realistic per-day durations exist — use those rather than guessing.

**Acceptance.** Course record has `timeRequired`; at least the day-mapped module pages carry a
per-page value; JSON still valid.

## 3. Add `hasPart` on the course-level record linking to each module

**Why.** Makes the whole ⇄ part relationship explicit in both directions — pages already point
up via `isPartOf`; this adds the down links. Recommended property.

**What.** Because module URLs are generated by Jekyll (and depend on the repo-name/`baseurl`
prefix), the most maintainable option is to build `hasPart` in `_includes/bioschemas.html` when
emitting the **course-level** record, instead of hardcoding URLs in the YAML.

Sketch (landing-page branch of the include) — iterate the module posts and emit a stub per
section:

```liquid
{%- assign course_modules = site.data.course.modules -%}
"hasPart": [
  {%- assign first = true -%}
  {%- for m in course_modules -%}
    {%- for p in site.categories[m] -%}
      {%- unless first %},{% endunless -%}{%- assign first = false -%}
      {
        "@type": "LearningResource",
        "name": {{ p.title | strip_html | jsonify }},
        "url": {{ course.url | append: p.url | replace: './/', './' | jsonify }}
      }
    {%- endfor -%}
  {%- endfor -%}
]
```

Caveats to resolve while implementing:
- The current landing-page branch emits `{{ course | jsonify }}` as a single blob. Adding
  `hasPart` means either (a) adding a static `hasPart` to the YAML, or (b) switching the
  landing branch to hand-built JSON (like the per-page branch) so Liquid can inject the loop.
  Option (b) is more work but keeps URLs correct without duplication.
- Reuse the same `course.url + page.url` join used for per-page `url` (strip the duplicate
  slash) so absolute URLs stay consistent.

**Acceptance.** Course-level record lists every section under `hasPart` with correct absolute
URLs; each URL matches the corresponding page's own `url`; JSON valid.

## 4. Add per-page `teaches` to more module pages

**Why.** `teaches` (learning outcomes) is Recommended and currently only set where added to
front matter. Bloom's-taxonomy-style outcomes are encouraged by the profile.

**What.** Add a `teaches:` list to the front matter of the hands-on module posts, e.g.:

```yaml

  - "Normalise a feature table by rarefaction and by composition, and explain the trade-offs"
```

The include already emits per-page `teaches` when present — no code change needed.

**Priority pages** (practical sections with clear outcomes): NumEcology normalisation,
alpha-diversity, diff-abundance; Analysis eda, beta-diversity, simple-networks; Workflow;
Setup.

**Acceptance.** Each listed page emits a non-empty `teaches` array; JSON valid.

## How to re-validate after any change

1. Build the site: `docker compose up` (or a one-off `jekyll build`).
2. Confirm every `application/ld+json` block still parses and keeps all Minimum properties.
   Re-run the same check used previously: extract the JSON-LD from `_site/**/index.html`,
   `json.loads` each block, and assert `name`/`description`/`keywords`/`url` + `dct:conformsTo`.
3. Optionally paste a deployed page URL into the online
   [Bioschemas validator](https://validator.bioschemas.org/) or Google's
   [Rich Results Test](https://search.google.com/test/rich-results).
